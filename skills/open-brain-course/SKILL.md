# Open Brain — Course (v3.1, level-based training)

## Fundamental change from v2.x

v2 was a reading course with practice at the end. v3 is level-based training:
the learner FIRST demonstrates vocabulary, THEN produces written answers, THEN
solves new practical cases. Each phase has a gate: you don't advance without a minimum score.

Evaluation happens inside your Claude session (your subscription), not through the API.
The learner downloads their answers from the HTML course as `practice-export.md` and saves it in the
course folder → the `open-brain-course-evaluate` skill reads it from the vault → evaluates → writes the
diagnosis and the next course.

## Model

**Claude orchestrates · the script executes · the browser consumes course.html.**

## Locating the engine

The engine is `$OPEN_BRAIN_ENGINES/course-engine/course_build.py`.
Run it from the vault root (`$OPEN_BRAIN_VAULT`, the folder that contains `Resources/`). The script
autodetects the vault. Override with the env var `VAULT_ROOT` (set it to `$OPEN_BRAIN_VAULT`).

## 3-phase flow

### Phase 1 — collect (script, no thinking needed)

```bash
python3 "$OPEN_BRAIN_ENGINES/course-engine/course_build.py" collect "<Domain>" "<Skill>"
```

Validates preconditions, scaffolds the Skill dir if missing, reads the curated `feeder-pns.md`
(authoritative), scans for suggestions, reads shipped gaps/friction/Cases, reads
`next-course-brief.md` if it exists, decides the mode and writes
`Skills/<Domain>/<Skill>/course-spec.json`. Returns JSON. If `{"ok":false}`, stop.

### Phase 2 — YOU write the content (the only point where you think)

1. Read `course-spec.json` (small and structured — do NOT load the whole vault).
2. If `course-spec.json.next_course_brief` exists, use it as priority input:
   the course must repair those gaps or raise the difficulty. Do not generate a general course
   from scratch unless the brief is empty or incoherent.
3. Read `course-spec.json.mastery` — this skill's state in the cross-skill graph
   (`Skills/skill_mastery_state.yaml`, a gate model:
   `no_expuesta → aprendiendo → gate1 → gate2 → gate3 → automatizada`, i.e.
   not exposed → learning → gate1 → gate2 → gate3 → automated; the enum values are engine identifiers, keep them as is).
   - `prerequisite_warnings`: prerequisites below gate2. **Not blocking** —
     they are recommendations ("the graph can't be rigid").
     If there are warnings, mention them in your final report but generate the course anyway.
   - `scaling_hint`: governs how you write the Transfer phase — see section C.

#### A) concept_primer — the learner's Vocabulary phase

Write 5-9 minimal concepts/vocabulary items. Each concept:
- `term`: the concept
- `definition`: definition in beginner language
- `example`: a concrete example
- `anti_example`: a common confusion or anti-example
- `why_it_matters`: why it unlocks the skill
- `quiz`: object with `question` (recognition question), `options` (3 options),
  `correct_index` (0-based). The quiz is the Phase 1 gate.

If vocabulary is missing, the learner fails through the expert blind spot, not through lack of effort.
The first-level quiz MUST cover every concept with a question that is NOT trivial
(not "what is X?", but "which of these is an example of X?").

#### B) modules — the learner's Production phase

Apply the INVERTED Pedagogical Spine: production first, reading after.
Each module must have:

1. `pretest`: a question the learner answers BEFORE reading anything in the module.
   This is not decorative — it is the signal of where they start.
2. `concept`: concept with a concrete example FIRST, technical term after.
   2+ paragraphs.
3. `quote`: a literal quote AFTER the example, never before.
4. `application`: 2-3 applications to the learner's real contexts.
5. `comprehension`: comprehension question + a reasonable answer.
   The learner WRITES their answer. It is evaluable.
6. `teaching`: an "explain it to X" prompt. Evaluable.
7. `anti_patterns`: at least 2 in "action → consequence" format.
8. `flashcards`: with `concept`, `front`, `back`, and an optional `quiz`.
9. `effort_check`: **fixed, do not vary it** — `{"question": "Was this hard, or did it
   come easily?", "options": ["it was hard", "normal", "it came easily"]}`. The engine
   already renders it; you only need to include it in each module's JSON. It is the
   illusion-of-learning diagnostic (Barcaui): a module that felt
   "effortless" is suspected of surface fluency, not real mastery —
   `open-brain-course-evaluate` later crosses it against the real score.

If there is no learner profile, use neutral language: `your company`, `your product`.

#### C) scenarios — the learner's Transfer phase (NEW in v3)

Write 2-3 transfer scenarios. Each scenario:
- `title`: name of the scenario
- `context`: a realistic situation where someone needs to apply the skill.
  Include: who the client/stakeholder is, what they want, what constraints they have.
  Do NOT use the same examples as in the modules.
- `constraint`: a constraint that forces a choice (time, budget, audience,
  channel, format). Without a constraint the exercise is too open.
- `deliverable`: what the learner must produce (a hook, a structure, a message,
  an argued decision). It must be concrete and evaluable.
- `evaluation_criteria`: 3-5 criteria the answer will be evaluated against.
  Each criterion: `name` + `description` of what demonstrates mastery.
- `expert_reference`: the expert's reference answer (NOT shown to the learner
  during the course — used only in evaluation).
- `effort_check`: the same fixed field as in the modules (see point 9 of section B).

Scenarios are the mandatory close. Without them, the learner knows vocabulary
but can't transfer. The typical learner complaint they answer: "if tomorrow I get
another case like that one, I wouldn't know what to say."

**Append-only scaling when `mastery.scaling_hint == "append_constraint"`**
(validated by Bastani et al. / LAT — Kim et al. 2026): do NOT invent a new scenario
from scratch. Take the scenario from `mastery.previous_scenarios` you want to
scale (same `context`, `deliverable`, base `evaluation_criteria`) and add
**exactly one** new atomic constraint on `mastery.suggested_constraint_dimension`
(canal | presupuesto | stakeholder | plazo | formato — i.e. channel | budget | stakeholder | deadline | format;
engine identifiers) to the `constraint` field. Do not
touch the rest of the scenario. This is what guarantees monotonic difficulty without
you having to judge "how much harder" by eye — the paper shows that
append-only is the only one of the three strategies (append/rewrite/reset) that
guarantees it. If `scaling_hint == "new_scenario"` (insufficient mastery, or the brief
asks for repair), write new scenarios as usual — don't force the append
on a base that isn't solid yet.

#### D) Write course-content.json

Write `Skills/<Domain>/<Skill>/course-content.json` following
the spec's `expected_content_schema` exactly. Include the 3 blocks: concept_primer,
modules, scenarios.

7. Run the anti-expert-blind-spot check: would someone who has never heard of the topic understand it?
   Which step am I taking as obvious? If something fails, decompress.

### Phase 3 — render (script, no thinking needed)

```bash
python3 "$OPEN_BRAIN_ENGINES/course-engine/course_build.py" render "<Domain>" "<Skill>"
```

Fills the template with the engine's built-in design system:
- **Tab 1 — Vocabulary**: interactive Concept Primer with a quiz per concept.
  Gate: ≥70% correct to unlock Tab 2.
- **Tab 2 — Production**: modules with pretest-first + writing exercises.
  Gate: all exercises attempted (answered or i_dont_know) to unlock Tab 3.
- **Tab 3 — Transfer**: practical case scenarios.
  No gate — but the learner should complete at least 1 scenario before exporting.
- **Export**: "Download practice-export.md" (Blob download, no server) and "Copy markdown" buttons, at the
  end of Transfer and at the end of Practice. Answers are kept in the browser's localStorage until exported.
  "Copy prompt + answers" copies a self-contained evaluator prompt plus the export, for evaluating in any
  Claude chat; the reply can be pasted back and downloaded as `course-evaluation.md`.
- **Sync (optional)**: only if you run your own sync endpoint. The button POSTs to
  `http://127.0.0.1:8005/api/practice-sync` (`COURSE_SERVER` in the template) with `{domain, skill,
  filename, markdown, …}`; your endpoint just writes `markdown` to
  `Skills/<Domain>/<Skill>/practice-export.md`. No such server ships with Open Brain; if nothing answers,
  the page tells the learner to use Download instead.

Emits flashcards to `Resources/Flashcards Logs/` and updates `course-history.md`.

## Evaluation — integrated flow (no API)

1. The learner completes the 3 phases in course.html.
2. Clicks "Download practice-export.md" (or "Copy markdown" and pastes it into a new file).
3. Saves the file as `Skills/<Domain>/<Skill>/practice-export.md` — the same folder as `course.html`.
   It holds every answer, state, quiz score, effort check and scenario answer (format:
   `practice-export/1`, documented in `open-brain-course-evaluate`). If you run your own sync endpoint,
   "Sync to the vault" writes the same file for you.
4. The learner says in their Claude session: `course-evaluate` or `evaluate the <Skill> course`.
5. The `open-brain-course-evaluate` skill reads `practice-export.md` + `course-content.json`
   directly from the vault, evaluates with the rubric, and writes:
   - `course-evaluation.md`
   - `next-course-brief.md` (if applicable)
6. The next course generated with this skill reads the brief automatically.

**No API. One file saved into the vault, then Claude + the vault.**

## Your final report (short)

```
✅ Course generated: Skills/<Domain>/<Skill>/course.html (v<N>)
Mode: <learning|review> · <X> modules · <Y> flashcards · <Z> scenarios.
Mastery: <state> · scaling: <append_constraint|new_scenario>
[If prerequisite_warnings]: ⚠️ weak prerequisites: <list> (not blocking)
To open: open "Skills/<Domain>/<Skill>/course.html"
```

Don't explain each module — the user sees it in the HTML.

## Declaring prerequisites between skills (optional)

If this skill depends on another one already generated, add to `Skills/<Domain>/<Skill>/meta.md`:

```yaml
prerequisitos:
  - "Marketing/Positioning execution"
```

(`prerequisitos` is the key the engine reads; keep it as is.) Exact `Domain/Skill` format (matches the folder in `Skills/`). Rule:
**only direct, operational prerequisites**
("do you need to master X to be able to do Y?", not "would it be nice to know it
first?"), maximum 3 per skill. `collect` reads them and validates them against
`skill_mastery_state.yaml` on every generation — without blocking.

## What this skill NO LONGER contains (it lives in the engine)

- Precondition validation and scaffolding
- Search for feeder PNs and suggestions
- Reading gaps, friction, shipped Cases
- Detection of the pedagogical mode
- Design system, render, tabs, gates, practice-export.md export (and the optional sync call)
- Flashcards JSON, history

## Rules kept as judgment (not migratable)

- HARD RULE: never generate a review course on mostly provisional material.
- The concept comes with a concrete example BEFORE the technical term.
- The literal quote comes AFTER the example, never before.
- At least 2 anti-patterns per module in "action → consequence" format.
- Practice must never depend on revealing the answer. The learner writes first.
- Transfer scenarios do NOT repeat examples from the modules.
  They must be new situations that force the learner to apply, not recall.
- The `effort_check` is a self-report, not an evaluation — never use it to
  score right/wrong directly. It only feeds the false-positive cross-check
  in `open-brain-course-evaluate`.
- Prerequisites in the cross-skill graph are recommendations, never blocks.
  If the user wants to generate an advanced course on a weak base, go ahead —
  an explicit override is allowed.

## Note on `Skills/skill_mastery_state.yaml`

A persistent (YAML) record of the state of each generated skill — don't edit it
by hand except to correct something obviously mis-inferred. It is written by `collect`
(it creates the entry the first time it sees the skill) and updated by
`course_build.py record-outcome`, called by `open-brain-course-evaluate` when closing a
course. Hygiene principle: better conservative than optimistic
— if there is no clear evidence of mastery, the state stays at `aprendiendo` (learning).
